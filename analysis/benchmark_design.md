# What an excellent benchmark should contain

This assessment distinguishes the **implemented v0.1 pilot** from **proposed improvements**. The pilot measures whether an agent can produce a standalone Python implementation of one specified financial workbook under a bounded workflow. It does not validate general financial judgment, production readiness, or investment decisions.

## Research basis

The following primary sources informed this assessment:

1. **HELM — _Holistic Evaluation of Language Models_.** Defines scenario coverage and omissions, measures multiple dimensions, and controls adaptation when comparing systems. Also discusses prompt sensitivity and contamination uncertainty. [Paper, introduction and §§1–1.1](https://arxiv.org/html/2211.09110).
2. **HumanEval — _Evaluating Large Language Models Trained on Code_.** Evaluates generated programs through functional execution, defines sampling-based pass@k, and highlights sandboxing untrusted code. [Paper, §§2–3](https://arxiv.org/html/2107.03374); [official evaluation harness](https://github.com/openai/human-eval).
3. **EvalPlus — _Is Your Code Generated by ChatGPT Really Correct?_** Shows that weak test suites can accept incorrect code and change rankings. Uses input mutation and differential testing; discusses test coverage, mutation analysis, and ambiguous specifications. [Paper](https://arxiv.org/html/2305.01210); [official repository and corrections](https://github.com/evalplus/evalplus).
4. **SWE-bench Verified.** Reviews task clarity and unfair tests, separates task-solving checks from regressions, and recognizes that environment failures can masquerade as model failures. [Official methodology](https://openai.com/index/introducing-swe-bench-verified/).
5. **Inspect.** Records evaluation configuration, usage, scores, status, errors, and retry history separately; an interrupted run is not automatically a scored failure. [Official evaluation-log documentation](https://inspect.aisi.org.uk/eval-logs.html).

These sources support evaluation-design principles. They do **not** independently certify this workbook, oracle, financial conventions, or pilot results.

## Design checklist and present assessment

| Priority | Criterion | What this pilot already provides | What is still needed |
|---|---|---|---|
| P0 | Explicit construct and unit | A one-workbook, one-program, model-plus-agent task with a JSON contract | Multiple independently motivated financial tasks before broad claims; explicitly separate model-only and native-agent tracks |
| P0 | Valid specification and oracle | Public active-branch assumptions; Python reference; 36 base-case comparisons with original workbook cached values | Independent financial review; changed-input reconciliation against an independently recalculated workbook/engine; tolerance review |
| P0 | Tests that detect realistic mistakes | Nine targeted scenarios, four seeded scenarios, intermediate-output scoring, a hard-coded-answer control | Mutation/defect analysis: wrong tax treatment, discount timing, terminal reinvestment, growth weights, capital weights, and option/share bridge; alternative correct implementations to detect unfair rejection |
| P0 | Honest failure accounting | Every persisted attempt listed; frozen zero-score submission retained; quota/outage attempts have null scores | Pre-register recovery/retry policy, completion criteria, and operator intervention rules for the next campaign |
| P0 | Controlled comparison | Matching prompt/input hashes for four terminal runs; common tool, call cap, execution timeout, and wall deadline | Match or explicitly stratify generation settings, auth/service tiers, context and token budgets; randomize/balance run order; do not attribute native-client differences solely to models |
| P0 | Reproducible evidence | Exact frozen submissions, per-case grades, accepted-execution hashes, sanitized ledgers, current source hashes, offline replay commands | Immutable per-run harness/client build attestations, fully locked runtime provisioning, resolved backend IDs where providers expose them; controlled workbook distribution rights/access |
| P1 | Meaningful coverage | Horizon, rate, capital-structure, reinvestment, growth-mixture and invariance checks | Contract-valid endpoints and numerical boundaries; more workbook/model families and independent tasks rather than merely more similar random inputs |
| P1 | Genuine future holdout | Original agent workspaces excluded reference code and held-out inputs | Treat released v0.1 cases as public regression/reproduction material; author and independently review a new holdout, record access/disclosure, and prohibit tuning on it |
| P1 | Repeats and uncertainty | Descriptive attempt-level observations; no unsupported confidence interval | Predefine the estimand, sampling protocol and task population; use fresh-state repetitions and analyze at independent run/task level, respecting workbook/case clustering |
| P2 | Efficiency and operational metrics | Accepted calls, elapsed run intervals, native Gemini counters, failure reasons | Comparable usage and measured monetary costs across providers; separate request, turn, execution, token and wall-time budgets |
| P2 | Appropriate execution isolation | Configured macOS sandbox and credential/resource policies; exercised private-file/symlink/network, output/time, and fresh-workspace checks | Direct fork/credential-canary and broader adversarial checks, independent security review, and separately validated portable runner; see the [tested-controls matrix](../BENCHMARK_SUMMARY.md#c-leakage-grading-exploits-and-evidence-gaps) |

P0 items are prerequisites for stronger claims; P1 expands validity and inferential usefulness; P2 improves operational reporting and portability. They are a proposed roadmap, **not completed features**.

## Why the primary judge is deterministic

The primary endpoint is executable numerical correctness, not whether a response sounds financially plausible. The grader compares the candidate's JSON outputs with reference calculations using explicit field weights and tolerances. No LLM awards the numeric score.

This removes judge-model subjectivity from the primary metric. It does not remove reference bugs, missing branches, insufficient coverage, ambiguous conventions, or weak tolerances. The base-case cache comparison is useful evidence; it is not an independent recomputation of every hidden scenario.

If explanation quality or maintainability is later evaluated by humans or an LLM, that should be a separate, versioned and validated endpoint—not silently blended into the numerical score.

## Statistical claims to avoid

- Thirteen related scenarios are **not thirteen independently sampled model performances**. They share one submitted program and one workbook family.
- Regrading the same frozen program checks deterministic replay, not generation reliability.
- Two perfect artifacts do not establish model equivalence. One unsuccessful submission followed by a successful one does not establish a learning trend.
- An interrupted Gemini run does not complete a paired comparison with Mistral, even when their native execution intervals overlap.
- The heterogeneous API/browser/pilot/recovery history is not a valid pass@k experiment. HumanEval's pass@k concerns multiple generated candidate programs per task under a specified sampling protocol; the number of hidden cases is not k.
- There is no defensible universal number of trials. Choose repetitions from the intended precision, observed variability, task heterogeneity and cost; expand independent tasks as well as repeated runs.
- A 100/100 score means full credit on this disclosed suite. It is not proof of universal correctness, contamination absence, finance expertise, or deployment safety.

## Recommended next campaign

1. Freeze a reviewed specification, oracle, grader, harness, runtime and publication/retry policy before generation.
2. Retain v0.1 as a public reproduction suite; construct a new independently reviewed holdout across more financial-model families.
3. Define whether the endpoint is first-attempt task success, success within a fixed attempt budget, or operational completion. Report numerical correctness and infrastructure availability separately.
4. Use fresh isolated state and balanced run order. Keep native-agent results distinct from any common-scaffold model-only comparison.
5. Record every attempt and recovery, including failures, with immutable artifact hashes and available backend/usage information.
6. Choose replication and uncertainty analysis at the task/run level; do not inflate sample size with correlated assertions.
7. Publish sanitized evidence and an amendment history. Never replace a failed frozen submission with a later or rejected answer.
